# Tenant-wide Alert Dashboard Implementation Plan

## Goal

Build a demo-stage frontend that shows all C5 alert records grouped by tenant, without tenant login. The dashboard consumes persisted alert data generated by the daily pipeline and surfaces the latest operational issues for each tenant.

## Core flow

1. Daily scheduler triggers a tenant-wide run.
2. For each tenant, the pipeline executes the tenant-scoped C3 context generation with no vendor filter.
3. C4 insight engine evaluates anomalies over the tenant aggregate.
4. C5 agent processes anomalies and generates alert summaries and recommended actions.
5. The alert payload is stored in DuckDB.
6. The frontend reads persisted records and displays them grouped by tenant.

## Tenant-wide processing rule

The scheduled job must always run as:

- tenant_id selected
- vendor omitted
- period = latest completed period
- grain = month by default

This ensures the C3 response is the tenant aggregate with vendor groups, and the alert logic is based on the overall tenant-level drift rather than a vendor slice.

## Daily pipeline design

### Phase 1: scheduled run

The scheduler runs once per day and loads the latest completed period. It should:

- identify all tenant ids
- for each tenant, compute tenant-wide C3 context
- evaluate C4 anomalies
- pass anomalies to C5
- store resulting alert records
- mark the run as complete

### Phase 2: deduplication

To avoid repeated alerts for the same tenant/period/KPI, store a fingerprint or unique constraint based on:

- tenant_id
- period
- grain
- kpi
- alert signature

This keeps the alert queue stable while allowing status updates and acknowledgement actions.

### Phase 3: UI category model

The frontend should render:

- alerts grouped by tenant
- per-tenant count by severity and status
- list + detail panel
- search/filter by tenant, status, priority, and KPI

## Frontend behavior

The UI is demo-stage and does not implement tenant logins. The assumptions are:

- one shared dashboard view for all tenants
- all alerts visible in one feed
- tenant filters available for quick narrowing
- alerts grouped by tenant in the list view

Preferred UX:

- summary cards at top
- filter bar below summary
- alert table/list in the center
- detail panel on the right or below the list

## Delivery plan

### Milestone 1: architecture and docs

- define alert schema
- define scheduled job design
- define DuckDB persistence tables
- define frontend requirement for tenant-wide alerts

### Milestone 2: backend persistence support

- add alert_run and alert table creation logic
- add a save_alerts function from C5 output
- add polling or API endpoint for alert retrieval

### Milestone 3: frontend dashboard

- fetch alerts by tenant
- render summary cards
- render grouped tenant list and detail view
- support status and severity filtering

### Milestone 4: daily orchestration

- run the tenant-wide pipeline automatically
- store results in DuckDB
- confirm the dashboard reflects the latest scheduled run

## Notes

- This is intentionally demo-stage: no login, no multi-tenant isolation in the UI layer.
- All alert visibility is global across tenants for the dashboard, with filters for easy segmentation.
- The alert feed should draw from the stored C5 output, not from ad hoc recomputation.

## Implementation Status

Milestone 2 is implemented:

- `backend/alerts.py` creates `alert_runs` and `dashboard_alerts` tables and persists C5 output with stable anomaly IDs.
- `GET /alerts` returns persisted records with optional `tenant_id` and `status` filters.
- `POST /alerts/run` scans every tenant at tenant aggregate scope, explicitly omitting vendor and office dimensions, then persists C5 results.
- The React dashboard loads the persisted feed from `VITE_API_URL` (default `http://localhost:8000`) and only refreshes data; pipeline execution belongs to the scheduler.
- Local frontend origins on ports 4173 and 4174 are enabled in the FastAPI CORS configuration.

Milestone 4 scheduler entry point is implemented:

- `python -m backend.scheduler --once` runs the latest available completed period.
- `python -m backend.scheduler` keeps a daily local-time scheduler alive, defaulting to 02:00.
- The scheduler calls the running API over HTTP, avoiding a second DuckDB connection and write-lock conflicts.
- Both modes process tenant aggregates only and follow `ENABLE_REASONING` from `.env`.
- Use `--disable-reasoning` for a quota-safe run or `--enable-reasoning` to override the environment setting.
